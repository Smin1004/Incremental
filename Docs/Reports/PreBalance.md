## 1. A. 시간제 판 (28 §2)

### 1.1 만든 것

- **판 시간.** `GameParams.runTimeSec` **30초**. 홀드와 상관없이 1초에 1씩 줄고 0이면 판이 끝난다(`Session.TickClock`). 결말 연출 중에는 멈춘다(예전 스태미나와 같다).
- **노드.** 시간 축(210°)의 노드 11개가 `run_time`(+초) 스탯이 됐다. **노드 id는 그대로**(`r1_stamina`, `r3_drain`, … `r11_stamina`)라 세이브의 레벨이 그대로 산다.
  - 임시 값: **링마다 +9초**. 링 1은 1레벨 +9초, 링 2~10은 2레벨 × 4.5초. 링 10까지 다 사면 **+90초**(링 11 판 120초). 링 11 끝없는 노드는 레벨당 4.5초.
  - 값은 `SkillTreeSeed.RunTimePerRing` 하나에서 나온다. 밸런스 패스가 링별로 다르게 하려면 시드의 줄만 고치면 된다.
- **HUD.** 위쪽 막대가 "**남은 시간 N초**"(같은 자리, 같은 색 변화와 깜박임). 막대의 최대값은 판 시작 때의 판 시간이다.
- **지운 것.** `F10` 소모 프리셋, `G` 게이지 모드(중력 고리를 게이지로 쓰던 그림 포함), `L` 키와 `staminaNodeScale`(·`Steps`), 소모 감소 상한(`maxReduction`은 필요 질량 감소에만 남았다), 스태미나 문자열 전부, 스태미나 프리셋 검사.
- **`Home`** = 남은 시간 0 (토스트 "남은 시간 0 (런 종료)").
- **`run_log.csv`.** `stamina_max`, `stamina_idle_drain`, `stamina_hold_drain` 세 열이 **`run_time`** 한 열이 됐다. 종료 사유 `stamina` → **`time`**. 헤더가 바뀌어 첫 기록 때 옛 로그는 `run_log_<시각>.csv`로 옮겨진다(기존 동작).
- **세이브 v4.** 마이그레이션: 기록(`runHistory`)의 `stamina` 종료를 `time`으로 바꾼다(그래야 지난 판 대비·최고 수입의 기준으로 계속 쓰인다). 노드 레벨은 손대지 않는다. 진행 중이던 판은 원래대로 로드 때 충돌 판으로 닫힌다(수입 유지). 기록의 옛 스태미나 수치는 읽지 않을 뿐이다.
- `UITheme`의 `stamina*` 필드는 `time*`으로 이름을 바꿨다(`FormerlySerializedAs`라 에셋 값 그대로).

### 1.2 확인 방법

- 판을 시작하면 위쪽 막대가 "남은 시간 30초"부터 줄어든다(링 1, 아무것도 안 샀을 때). 홀드하든 안 하든 같은 속도.
- 트리의 시간 축 노드 툴팁: "판 시간 +9초" / "+4.5초".
- `Home`: 즉시 판 종료.

### 1.3 확인한 것

- 에디터, 링 1: 판이 **정확히 30.0초**에 끝났고 `run_log.csv`에 `run_time=30`, `end_reason=time`.
- 판 시작 시점 기록: 링 1 30초 → 링 11(링 10까지 전부) 120초 (`Proto11Tests`).

### 1.4 개발자 세이브 (복사본으로 확인)

`save.json` 복사본을 새 코드로 열었다: **v3 → v4로 정상 로드**, 링 11, 재화 그대로, 노드 레벨 83개 그대로, 기록 18판 중 스태미나 종료 2판이 `time`으로 바뀜, **판 시간 165초**(120초 + 링 11 끝없는 노드 Lv10 × 4.5초). 진짜 `save.json`은 작업 내내 원본과 같았다(`cmp`).

## 2. B. 홀드 토글 (28 §2.1)

- `settings.json`의 **`holdToggle`** (기본 끔). 켜면 **클릭 한 번 = 누르기 시작, 다시 클릭 = 놓기.** 판이 시작될 때와 끝날 때 놓은 상태로 돌아간다. 일시정지·결말 중 클릭은 무시한다.
- 클릭 감지는 `Update`에서 한다(고정 틱은 클릭한 프레임을 놓칠 수 있다). 게임 로직은 그 상태를 마우스 버튼 대신 읽는다.
- **디버그 키 `H`**: 켜고 끔, 토스트 "홀드 토글: 켜짐 (H, 클릭 한 번 = 누르기, 다시 클릭 = 놓기)", `settings.json`에 저장(다음 실행에도 유지). F1 오버레이에 "홀드 토글 켜짐/꺼짐 [H]".
- 콘솔 `[Feature] hold toggle: holding / let go`.
- 확인: 에디터에서 토글 켬 + 누름 상태 → 입력이 "누름", 놓음 → "놓음". 실제 클릭은 Game 뷰 포커스가 필요해 개발자 확인으로 남긴다.

## 3. C. 봇이 증폭 결정을 먹으러 간다 (27 §1.1 P1)

- 결정이 화면에 있고, **남은 수명 안에 중력 범위까지 닿을 수 있으면** 봇이 결정 쪽으로 간다. 닿는 시간 = (결정까지 거리 − 중력 반지름) ÷ (봇 커서 속도와 중력원 추종 속도 중 느린 쪽) + 여유 0.3초. 결정이 끌려오기 시작하면 다시 가장 빽빽한 먼지 칸으로. 공명(2중첩)도 같은 규칙(먼저 나온 결정부터 가장 가까운 것).
- 봇 필드: `chaseCrystals`(켬), `chaseMarginSec` 0.3. 봇의 다른 값(`moveSpeedPx` 등)처럼 봇 컴포넌트에 있다(측정 도구라 데이터 에셋에 넣지 않았다).
- 콘솔 `[Bot] going for the crystal` / `back to the dust` (능력 로그가 켜져 있을 때).

### 결정 획득률 (링 2 시작 상태, 봇 5판, `Time.timeScale` 8)

링 2 시작 상태(`ApplyRingStartState(2)`)에는 **결정 해금 노드가 없다**(링 2 노드라 빠진다). 그래서 `ability_crystal`을 더해서 쟀다. 판마다 같은 상태로 되돌렸다.

| 봇 | 나온 결정 | 먹은 결정 | 놓친 결정 | 획득률 | 판 수입 (5판) | 평균 |
|---|---|---|---|---|---|---|
| **결정을 쫓는다 (11차)** | 15 | **14** | 0 | **93%** (나머지 1개는 판이 끝날 때 아직 화면에 있었다) | 27 / 37 / 30 / 37 / 35 | 33.2 |
| 쫓지 않는다 (예전) | 15 | 0 | 10 | 0% | 32 / 35 / 35 / 37 / 35 | 34.8 |

- **링 2에서는 결정을 먹어도 판 수입이 늘지 않았다**(오히려 −5%, 표본 5판이라 흔들림 안). 링 2의 판은 39초이고, 결정을 먹으러 가는 동안 빽빽한 먼지를 떠난다. 6초 버프(반경 ×1.20)가 그 손해를 메우지 못한다. 밸런스 패스에서 결정의 몫을 볼 때 참고할 숫자다(28 §6-4).

## 4. D. 진행 로그 (28 §4)

- 관문 노드를 살 때마다, 그리고 **새 게임의 첫 구매** 때 콘솔 한 줄과 `persistentDataPath/progress.csv` 한 줄.
  - 콘솔: `[Progress] gate gate_t2 at 5:15 (315 s of play), run 9, ring 2, currency 85 -> 17`
  - CSV 열: `event, node, play_time_s, play_time, run, ring, currency_before, cost, currency_after, wall_clock`
- **플레이 시간** = 새 게임 이후 판 + 결과 + 트리 화면의 시간(`MetaState.playClockSec`, 세이브에 저장). 일시정지(창 포커스 잃음 + `pauseOnFocusLoss`, 갤러리) 중에는 멈춘다. 게임 시간으로 재므로 봇이 배속으로 돌면 그만큼 빨리 찬다.
- **새 게임(`Shift+F9`)** 은 시계를 0으로 하고 `new_game` 줄을 남긴다. 한 파일에 측정 플레이 여러 번이 이어 쌓인다.
- v3 세이브는 시계를 `totalPlayTimeSec`(판 시간 합)에서 시작한다. 결과·트리 시간이 빠져 조금 늦다. 측정 플레이는 새 게임에서 하므로 상관없다.
- 확인 (봇, 새 게임): 첫 구매 `r1_spawn` **0:30**(1판), 링 2 관문 **5:15**(9판). 28 §4의 목표는 사람 기준 첫 구매 1분 안, 링 2 관문 4:00이다(봇은 사람보다 빠르다는 가정이니 참고만).

## 5. E. 블랙홀 원판 정리 (24 §24.3)

### 5.1 만든 것

1. **원판 안 먼지를 가장자리 밖으로** (`Lens.hlsl` `LensForwardPush`). 원판 안쪽의 먼지·리본 정점을 반지름 × (1 + `lensRingWidth`)부터 바깥으로 밀어 그린다. 가장자리에서 바깥쪽 렌즈와 이어지게(중심 → 1.08R, 가장자리 → 바깥에서 가장자리가 그려지는 자리). 원판 위에 먼지가 남지 않고 가장자리에 먼지 고리가 생긴다. 렌즈 세기 램프(들이마심 1초)와 연출 강도를 따른다. 끄기: `AbilityTable.blackHole.lensClearDisc`.
2. **작아진 천체의 코로나 축소** `blackHoleBodyGlowScale` **0.3**: 블랙홀이 천체를 작게 그리는 동안 그 천체의 글로우 도달 거리를 몸체 축소 위에 0.3배 더 줄인다.
3. **원판이 회색이던 진짜 원인 (조사 결과, 스펙과 다르다).** 24 §24.3은 "원판 안쪽 먼지가 원판 위에 더해져 그려진다"고 봤지만, **먼지(order 0)와 리본(−1)은 원판(order 11) 뒤에 그려진다.** 원판만 따로 그리면 완전히 검다. 원판을 회청색으로 씻은 것은 **점화 연출**이었다: 블랙홀이 열린 동안 중력원에서 별(티어 9~11)이 완성되면 `IgnitionFx`의 화면 플래시(order 60)와 빛 고리(order 55)가 모든 것 위에 그려진다. 같은 장면에서도 그 순간 별이 완성됐는지에 따라 원판이 검거나 회색이었다.
   - 고친 것: `blackHoleBodyGlowScale`과 같은 곳에 **`blackHoleIgnitionScale` 0** — 천체가 작아진 동안 점화한 별의 플래시와 빛 고리 배율. 1이면 예전과 같다.
   - 큰 청색 띠(10차 캡처의 원판 둘레 굵은 고리)도 그 빛 고리였다.

### 5.2 캡처 (링 11, 먼지 5,000, `StageRunScene` 같은 시드, 중력원 화면 가운데)

| 파일 | 내용 |
|---|---|
| `e_bh_ring11_open0_6_compare` | 열린 0.6초. 왼쪽 10차 그대로(원판 회청색, 점화 플래시) ↔ 오른쪽 11차(원판 검음, 가장자리 먼지 고리). 오른쪽은 중력원이 아직 가운데로 오는 중이라 블랙홀이 오른쪽 아래에 있다 |

## 6. F. 성능 조사 (27 §5 V4)

**조건.** 10/15, 어댑터 꽂음(`PowerLineStatus Online`), 1920×1080 독점 전체화면, vSync 0, 예열 2초 / 표본 6초, `-perfbench`. 같은 날 **대조군 `Builds/Win64_proto5` 세 번**(측정 시작·중간·끝). 개발 빌드, 측정 중 에디터는 열려 있되 놀게 두었다. 10/14 밤에 돌린 첫 측정은 노트북이 잠들고 배터리로 바뀌어 버렸다(`invalid_battery/`, 쓰지 않음).

**계측을 더했다.** `PerfBench` 두 번째 표: 능력 틱, 궤적 이력(먼지 틱 안의 몫), 그리고 `FrameTimingManager`의 메인 스레드 CPU / 렌더 스레드 CPU / GPU 시간(프레임당 ms). 이를 위해 `PlayerSettings.enableFrameTimingStats`를 켰다. 플래그 `-perfquick`, `-perfrefill`, `-perfoldradius`, `-perfnojobs`. Unity 프로파일러 마커(스크립트 Update 등)는 빌드·에디터 모두 값이 0이라 쓰지 않았다.

### 6.1 어디가 비싼가 (먼지 8,000 장면, 11차 이전 코드 = `-perfnojobs`, 4회 평균)

프레임 약 7.1 ms(141 fps). **메인 스레드 CPU가 프레임을 정한다**(메인 7.0 ms, 렌더 스레드 0.5 ms, GPU 2.0 ms — GPU는 메인 스레드와 나란히 돌아 기다리게 하지 않는다).

### 6.3 6~8차로 늘어난 몫 (빌드 확인 2차: 먼지 틱 +0.45 ms, 메시 +0.55 ms)

먼지 8,000, 능력 없음, `-perfnojobs`(이전 메시 코드), 각 2회 평균.

| 조건 | 평균 fps | 먼지 틱 ms | 메시 ms |
|---|---|---|---|
| 지금 값 | 142.1 | 0.99 | 3.11 |
| 보충 가속 0 (`dustRefillBoost` 3 → 0) | 143.5 | 0.94 | 3.02 |
| 옛 반경 (6차 전: 기본 180, 링 11 +95%) | 152.2 | 0.81 | 2.72 |

- **늘어난 몫의 약 75~80%는 중력 반경 축소다** (먼지 틱 +0.18, 메시 +0.39 ms). 반경이 작으면 잡히는 먼지가 줄어 **화면에 남는 먼지가 많다.** 먼지 하나의 비용이 아니라 먼지 수가 늘어서다.
- **먼지 보충 가속은 약 +0.05 / +0.09 ms**(약 15~20%).
- **능력 틱은 0.01 ms**(능력 없는 장면), 능력 트리대로 장면에서도 0.03 ms. 무시할 만하다.

### 6.4 만든 것

- **먼지 메시 Burst 잡** (`DustMeshRenderer.QuadJob`, `IJobParallelFor`, 묶음 256). 먼지 배열과 정점 배열을 고정(pin)해 포인터로 읽고 쓴다. 먼지 하나의 계산식은 그대로 옮겼다. `GameParams.dustMeshJobs` 끄면 같은 코드를 메인 스레드에서 차례로 돈다(비교용). `Incremental.asmdef`에 `Unity.Burst` 참조와 `allowUnsafeCode`를 더했다(Burst는 2D 패키지 의존성으로 이미 들어 있었다).
- 되돌린 궤적 잡 코드는 보고서 작성 시점 스크래치패드에만 있다. 밸런스 패스에서 먼지 상한을 올리게 되면 다시 꺼낼 후보다(설명: §6.1 3번).

## 9. 스펙과 다르게 한 것

1. **시간 노드 값**: 28 §2는 "링 10까지 +90초, 링 1 30초 → 링 10 120초"인데 둘은 동시에 맞출 수 없다(링 k에 들어설 때는 링 k−1까지의 노드만 있다). **링마다 +9초**로 해서 링 10까지 전부 사면 120초가 되게 했다(링 10 도착 때 111초, 링 11 120초).
2. **링 11 끝없는 노드**: 레벨당 4.5초(예전 스태미나 +9의 자리, 임시).
3. **원판 회색의 원인**이 스펙(24 §24.3)의 진단과 달랐다(§5.1-3). 제안된 두 가지(먼지 밀기, 코로나 축소)는 그대로 넣었고, 진짜 원인인 점화 연출 끄기를 더했다.
4. **결정 획득률 측정**: 링 2 시작 상태에 결정 해금이 없어 해금을 더해서 쟀다.
5. **봇 결정 쫓기 값**은 봇 컴포넌트 필드다(데이터 에셋이 아니라 다른 봇 값과 같은 곳).
6. **v3 세이브의 플레이 시계**는 판 시간 합에서 시작한다(결과·트리 시간은 알 수 없다).
7. **`EndReason.Stamina` → `TimeUp` ("time")**. 문자열이 바뀌어 옛 `run_log.csv` 줄과 다르다.
8. F의 측정 계측: Unity 프로파일러 마커는 빌드에서 값이 안 나와(에디터에서도 0) **FrameTimingManager**(메인 스레드 CPU, 렌더 스레드 CPU, GPU)로 바꿨다. 이를 위해 **`PlayerSettings.enableFrameTimingStats`를 켰다**(프로젝트 설정, 비용 미미).

## 10. 알려진 문제

1. 홀드 토글은 실제 마우스 클릭으로는 개발자가 확인해야 한다(에디터 MCP로는 Game 뷰 포커스가 없어 상태만 확인).
2. `17_Playtest_Guide` §1의 `F10`, `G`, `L` 줄 삭제와 `H` 추가는 기획 세션 몫이다.
3. 링 2 결정 쫓기는 수입을 늘리지 않았다(§3). 밸런스 패스에서 결정 버프 크기를 볼 때 참고.
4. 진행 로그의 시계는 게임 시간이다. 에디터에서 `Time.timeScale`을 바꾸면 그만큼 빨리 간다(봇 측정용으로 의도한 것).
5. F: 잡을 켜면 "나머지"(프레임 − 먼지 틱 − 메시 − 궤적)가 1.4 ms쯤 커 보인다(§6.1 ¹). 메인 스레드 CPU는 줄었다.
6. F: `FrameTimingManager`의 GPU 값이 가끔 몇 초짜리 쓰레기 값으로 온다. 1초 넘는 표본은 버린다. 첫 측정 몇 표에는 그 값이 섞여 있다(`quick_*_r1` 일부).
7. 빌드 확인 2차의 "6~8차로 늘어난 몫"은 같은 날 다시 재니 거의 재현되지 않았다(§6.3).
