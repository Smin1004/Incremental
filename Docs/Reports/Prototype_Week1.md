# 1주차 프로토타입 보고

| 항목 | 값 |
|---|---|
| 상태 | 객관 수치 기입 완료, 주관 항목은 개발자 플레이 후 기입 |
| 작성 | 2026-09-17, 구현 세션 |
| 대상 | 기획 세션. [11_Prototype_Spec.md](../11_Prototype_Spec.md) §10 순서대로 답한다 |
| 환경 | Unity 6000.0.66f2 에디터, Game view 1920×1080, Windows 11 노트북. 전부 에디터 수치이며 빌드 수치가 아니다 |

## 측정 방법

- 객관 수치는 F4 오토플레이 봇으로 얻었다. 봇 규칙은 세 줄이다: 화면을 12×7 격자로 나눠 먼지가 가장 많은 칸으로 커서를 초당 250px로 옮기며 홀드한다. 질량이 최고 해금 티어 임계에 닿으면 놓는다(게임이 그 시점에 자동 생성하므로 실제로는 계속 홀드와 같다). 런 사이에는 살 수 있는 항목 중 가장 싼 것부터 재화가 떨어질 때까지 산다(업그레이드와 해금을 같은 후보로 본다).
- 봇은 사람보다 못한 점이 하나 있다. 티어 2를 해금하기 전에 싼 업그레이드에 재화를 다 쓰므로 해금이 늦다. 사람은 저축을 선택할 수 있다.
- 런 로그는 `%USERPROFILE%\AppData\LocalLow\DefaultCompany\Incremental\run_log.csv`에 런마다 1행 추가된다(열: run, duration_s, income, t1, t2, t3, ratio_vs_last, 시작 시 업그레이드 레벨 5개). 이번 10런 측정 전의 기록(체크포인트 A·B 테스트와 개발자 수동 플레이)은 같은 폴더의 `run_log_before_C.csv`에 보관했다.
- 디버그 키: F1 오버레이(FPS, 먼지 수, 틱 ms), F2 성능 모드(dust_cap 1000, spawn_rate 100 런타임 오버라이드), F3 재화 +1000, F4 봇 토글, F12 스크린샷(위 폴더). 결과 화면에서 스페이스는 "다음 런"과 같다.

- 런당 포획 먼지는 120개(런 1)에서 290개(런 10)로 늘었다. 초당 2.4개 → 5.0개.

## 2. 홀드가 지루해진 시점

`[개발자 플레이 후 기입]` 10분 연속으로 플레이하면서 "놓고 싶다"고 처음 느낀 시각을 분 단위로 적는다. 없었으면 "없었음"이라고 적는다.

## 3. 스태미나 기본값과 런 길이

객관 수치.

- 스태미나 60, 대기 소모 0.2/초, 홀드 추가 소모 1.0/초. 계속 홀드하면 런은 50.0초, 한 번도 홀드하지 않으면 300초다. 봇은 상시 홀드라 런 길이가 정확히 50초(최대 스태미나 업그레이드 후 58.3초, 66.7초 순으로 늘어남)로 고정된다.
- 개발자가 체크포인트 A 직후 수동으로 플레이한 두 런은 165초와 203초였다(`run_log_before_C.csv` 6~7행). 역산하면 홀드 비율 10~16%로, 사람은 먼지가 모이기를 기다리며 놓고 있는 시간이 길다.

`[개발자 플레이 후 기입]` 런이 짧았는지 길었는지, 그렇게 느낀 순간이 무엇이었는지(먼지가 없어서 기다렸는지, 스태미나가 먼저 떨어졌는지) 한두 줄.

## 4. 프레임 수치

F2 성능 모드(생성 100/초)로 먼지를 채운 뒤 약 10초 동안 0.5초 창 FPS를 여러 번 읽어 평균했다. 에디터 Game view 1920×1080, 다른 창이 앞에 있는 상태(`Application.runInBackground = true`)에서 측정했으므로 실제 플레이보다 GPU 부담이 낮을 수 있다. 틱 ms는 FixedUpdate 한 번(먼지 이동·생성·포획·판정 전체)의 CPU 시간이다.

| 먼지 수 | 평균 FPS (측정 창) | 틱 ms (1초 최대) | 조건 |
|---|---|---|---|
| 300 | 167 (19.9초, 3,323프레임) | 0.09 (0.10) | 홀드 없음, 표류만 |
| 1,000 | 170 (25.3초, 4,304프레임) | 0.25 (0.31) | 홀드 없음, 표류만 |

- 300개와 1,000개의 FPS가 같다. 병목은 먼지가 아니라 에디터 오버헤드다. 시뮬레이션 비용은 먼지 수에 비례하지만 1,000개에서도 0.25ms로 고정 틱 20ms의 1.3%다.
- 봇이 홀드하며 플레이한 런 1~10 동안 오버레이 FPS는 187~190(먼지 120~300개)이었다.
- 프로젝트 품질 설정의 vSyncCount는 1이지만 에디터 Game view의 VSync 토글이 꺼져 있어 60을 넘는 수치가 나왔다. 빌드에서는 60fps에 고정된다.
- 렌더는 먼지 1개 = 쿼드 1개인 메시 하나를 매 프레임 재구성한다(1,000개 = 정점 4,000개). 드로우콜 1개.

## 5. "놓으면 생성" 규칙이 직관적이었는지

`[개발자 플레이 후 기입]` 처음 3런 동안 티어 1 임계(10) 미만에서 놓아 먼지가 흩어진 횟수, 최고 해금 티어에서 자동 생성되는 것을 언제 알아챘는지, 커서 게이지만으로 "지금 놓으면 무엇이 나오는지"를 알 수 있었는지 적는다.

## 6. 바꾸고 싶어진 수치와 이유

봇 수치에서 보이는 것.

- 혜성 해금 50이 초반에 멀다. 티어 1만으로는 런당 수입 12~17이라 런 1~3 수입을 전부 모아도 44다. 싼 것부터 사면 10런 동안 해금이 오지 않는다. 사람이 해금을 노리고 저축해도 3런은 걸린다. 후보: 해금 비용 50 → 25~30, 또는 소행성 판매가 1 → 2.
- 필요 먼지 수 감소(−4%/레벨)는 티어 1에서 3레벨까지 효과가 없다. 질량은 먼지 개수(정수)인데 임계 10 × 0.96 = 9.6은 여전히 먼지 10개가 필요하고, 9 이하가 되려면 −12%(3레벨, 비용 25+34+46)가 필요하다. 임계 25(혜성)는 1레벨부터 24개로 줄어 효과가 있다. 티어 1에서 체감되게 하려면 레벨당 −10%로 올리거나 임계를 올림이 아니라 내림으로 비교해야 한다.
- 초반 가치는 먼지 생성 빈도(+1/초 = +25% 먼지)가 가장 크고, 모으는 힘이 다음이다. 최대 스태미나(+10 = 런 +17%)는 비용 20으로 가성비가 좋은데 봇은 비용순이라 런 9에야 샀다. 봇 규칙의 한계이지 수치의 문제는 아니다.
- 커서를 한곳에 고정하면 유입이 초당 0.8개뿐이다(체크포인트 A 측정: 50초 정지 홀드에 소행성 4개). 표류 15px/초가 느려서 움직이지 않으면 아무것도 모이지 않는다. 의도라면 유지하고, 아니면 표류 속도를 올리거나 생성 위치를 커서 주변으로 편향시킨다.
- 생성 4/초로는 초기 100개에서 상한 300개까지 50초가 걸려, 런 1에서는 상한을 보지 못한다. 상한을 체감시키려면 초기 배치를 200 이상으로 올린다.
- 판매 배율 +25%로 수입이 22.5처럼 소수가 된다. 재화 표시는 내림이라 "1.75"가 "1"로 보인다. 판매가를 정수로 올림/내림할지 정한다.

`[개발자 플레이 후 기입]` 직접 플레이하며 바꾸고 싶어진 값과 이유. 위 목록에 동의하는지도 적는다.

## 8. 인계 메모

- 코드는 `Assets/Game/Scripts/`, 데이터는 `Assets/Game/Data/`(GameParams, CelestialTable, UpgradeTable), 씬은 `Assets/Game/Scenes/Prototype.unity`(빌드 씬 0번). 씬은 카메라·라이트·GameRoot 프리팹뿐이고 나머지는 코드가 만든다. `Incremental/Setup/Run All` 메뉴가 에셋과 씬을 다시 만든다.
- 스펙 표 밖의 연출 값(먼지 크기, 표류 노이즈, 흩어짐 속도, 행성 표시 시간, 팝 크기)도 GameParams에 있다. 코드 상수는 없다.
- 알려진 사항: 판매 배율 업그레이드 뒤 수입이 22.5처럼 소수가 되고 재화도 소수로 쌓인다(표시는 내림). 정수화 여부는 밸런스 패스에서 정한다. 해금은 순차(티어 2를 사야 티어 3 구매 가능).
- Unity 6 에디터는 다른 창 뒤에 있으면 플레이가 멈추므로 GameRoot가 시작 시 `Application.runInBackground = true`를 켠다. 봇 무인 실행에 필요하다.
