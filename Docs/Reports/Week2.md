## 1. 만든 것

**데이터와 구조**
- 업그레이드를 문자열 id로 식별한다(`spawn_rate`, `pull_accel`, `sale_mult`, `stamina_max`, `threshold_mult`, `dust_cap`, `dust_mass`, `gravity_radius`, `stamina_drain`, `start_bonus`). 저장, 로그, 문자열 키가 전부 이 id를 쓴다. 업그레이드 개수 상수와 enum 인덱스 배열은 없앴다.
- `UpgradeDef`에 `id`, `enabled`, `revealAtTier` 필드가 있다. 코드를 고치지 않고 항목을 끄거나 늦게 보이게 할 수 있다. 지금은 전부 켜짐, 티어 1부터 공개다.
- 티어 4~11, 새 업그레이드 5개, 해금 2~11을 에셋에 추가했다. 기존 항목은 그대로다. `Incremental/Setup/1. Create Data Assets`가 에셋에 없는 항목만 시드 코드에서 채운다.
- 데이터 에셋에 한국어가 없다. 티어 이름(`tier.N`)과 업그레이드 이름·효과 문구(`upg.<id>.name`, `upg.<id>.effect`)는 `UIStrings`의 id 키 사전에 있다.
- 메뉴 `Incremental/Validate Data`. 티어 번호 연속·오름차순, 필요 질량 증가, id 중복, 해금 대상 티어 존재, 문자열 키 존재를 검사한다. 추가로 판매가·비용·성장률 > 0, 모든 id가 `Stats.Compute`에 있는지, 2 이상 모든 티어에 해금이 있는지(순차 해금이 끊기지 않는지), 에셋과 시드 코드가 같은지(다르면 경고)를 본다.
- 업그레이드 대상 값 11개(생성 빈도, 모으는 힘, 판매 배율, 최대 스태미나, 임계 배율, 먼지 상한, 먼지 질량, 중력 반경, 대기 소모, 홀드 소모, 초기 먼지)가 전부 `EffectiveStats`를 거친다. 중력 반경 링도 업그레이드된 반경을 그린다.

**표기와 화면**
- `Fmt.Num`: 1,000 미만은 정수, 그 이상은 유효숫자 3자리. 문자 모드(1.23K … 999Dc, 그 위는 1.00e36)와 과학 모드(1.23e9). 재화·수입은 내림, 비용은 올림. 보이는 재화 ≥ 보이는 비용이면 실제로 살 수 있다(9.0e15 미만에서 정수 연산으로 정확, 테스트로 2만 쌍 확인).
- 결과·상점 화면을 2단으로 바꿨다. 왼쪽 결과(수입 64pt, 1개 이상 만든 티어만 2열, 지난 런 대비, 최고 수입, 다음 런), 오른쪽 상점(보이는 업그레이드 + 다음 해금 1행, 다 해금하면 "모두 해금"). 런 종료에서 다음 런까지 클릭 1회(스페이스도 된다).

**저장과 세션**
- `save.json`(진행)과 `settings.json`(표기 모드, 포커스 일시정지). 형식과 시점은 4절.
- 런 중 5초마다 진행 중인 런(pending)을 저장한다. 런 중 정상 종료는 결과 화면 없이 종료 처리(`quit`), 다음 실행에 pending이 남아 있으면 강제 종료로 처리(`crash`). 둘 다 그 런의 수입이 재화에 들어간다(02 §6).
- 저장이 없으면 런 1을 바로 시작하고, 있으면 결과·상점 화면에서 마지막 런 기록을 보여 주며 시작한다.
- 런 중 창이 포커스를 잃으면 로직이 멈추고 "일시정지"가 뜬다. 봇이 켜져 있으면 멈추지 않는다.

**런 통계**
- MetaState에 누적 수입, 누적 플레이 시간(런 길이 합), 티어별 누적 행성 수, 생성한 최고 티어, 전체 런 기록(runHistory)이 있다. 런 기록 항목: 런 번호, 길이, 수입, 티어별 개수, 지난 런 대비, id별 시작 레벨, 해금 최고 티어, 종료 사유.
- `run_log.csv`의 열은 테이블에서 만든다: `run, duration_s, income, t1..t11, ratio_vs_last, lvl_<id> ×10, end_reason`. 헤더가 바뀌면 기존 파일을 `run_log_<시각>.csv`로 옮기고 새로 시작한다.

**디버그 (에디터와 개발 빌드에서만)**
- F1 오버레이, F2 성능 모드, F3 재화 = max(재화 × 10, 1,000), F4 봇, F5 즉시 저장, F6 다음 티어 무료 해금, F7 표기 전환, Shift+F9 저장 삭제 후 런 1, F12 스크린샷.
- 메뉴 `Incremental/Save/Open Folder`, `Incremental/Save/Delete Save`(확인 창, 플레이 중이면 Shift+F9와 같다).
- 봇은 업그레이드 테이블을 순회한다. 전략은 1주차와 같다.

**코드 구조**
- asmdef 3개: `Incremental`(Assets/Game/Scripts), `Incremental.Editor`(Scripts/Editor), `Incremental.Tests.EditMode`(Assets/Game/Tests/EditMode).
- 파일 입출력은 폴더를 주입받는다(`SaveStore`, `RunLogger`). 테스트는 임시 폴더만 쓴다.

## 3. 기획 세션이 정해야 할 것

1. **제안 업그레이드 5개의 채택과 공개 시점.** 지금은 전부 켜져 있고 런 1부터 보인다. 10 §4.3의 "먼지 폭증(15~20분)"을 만들려면 `dust_cap`과 `gravity_radius`의 `revealAtTier`를 같은 구간(티어 3~5 해금 무렵)으로 맞추는 안이 있다. 끄는 것은 에셋의 `enabled`만 바꾸면 된다.
2. **질량 초과분.** 최고 해금 티어의 임계에 닿으면 즉시 생성하고 질량을 0으로 만든다(1주차 규칙). `dust_mass`가 커지면 먼지 1개가 임계를 수백 배 넘어도 초과분이 사라진다. 티어 1만 해금한 상태에서 먼지 질량 3,325짜리 1개가 소행성(판매가 1) 1개가 된다. 초과분을 버릴지, 다음 생성으로 넘길지, 여러 개를 만들지 정해야 한다. 먼지 질량이 "티어 6 이후 주력"(02 §3)이면 밸런스 전에 정하는 편이 낫다.
3. **"지난 런 대비"에 quit·crash 런을 넣을지.** 지금은 직전 런이 무엇이든 그 수입과 비교한다. 10초 만에 끈 런(수입 2) 다음 런은 배율이 크게 튄다. 스태미나로 끝난 직전 런과 비교하는 안이 있다.
4. **런 중 종료(quit) 때 홀드 중이던 질량.** 지금은 버린다(crash와 같게). 스태미나로 끝날 때는 1주차 규칙대로 강제 생성한다. quit도 강제 생성할지 정해야 한다.
5. **`enabled=false`의 의미.** 지금은 이미 산 레벨의 효과까지 끈다. "새로 못 사게만" 하려면 바꿔야 한다.
6. **큰 배율 표시.** "지난 런 대비"는 11 §4대로 `×1.00` 형식이라 치트를 쓰면 `×347409153.13`처럼 길어진다(화면에는 들어간다). 정상 플레이에서는 ×1~×10대라 문제가 없을 것으로 보지만, 해금 런(목표 ×3 이상)에서 큰 값이 나오면 `Fmt.Num` 표기(×347M)로 바꿀지 정한다.
7. **숫자 표기 세부.** 접미사 K, M, B, T, Qa, Qi, Sx, Sp, Oc, No, Dc와 뒷자리 0 유지(1.00K, 12.0M)가 맞는지. 1.20K처럼 보이는 것이 싫으면 0을 지우는 안이 있다.
8. **해금 행의 판매가 표시.** 상점의 해금 행 효과 칸에 "티어 5 · 판매가 2.00K"(판매 비용 업그레이드 반영)를 보여 준다. 결과 화면 항목은 늘리지 않았다.
9. **1주차에서 이어진 것.** 판매 배율 때문에 재화가 소수(22.5)로 쌓인다. 표시는 내림이다. 정수화 여부는 여전히 미정이다.

## 4. 저장 파일 형식

위치: `%USERPROFILE%\AppData\LocalLow\DefaultCompany\Incremental\` (`Application.persistentDataPath`). JsonUtility. NaN은 쓰지 않고 "없음"은 -1이다.

**save.json** (압축 JSON)

| 필드 | 형 | 내용 |
|---|---|---|
| `version` | int | 1. `SaveMigration.Migrate`가 이 값으로 단계를 고른다. 지금은 단계가 없다 |
| `meta.currency` | double | 재화 |
| `meta.upgradeLevels` | `[{id, level}]` | 업그레이드 레벨. 테이블에 없는 id는 무시하되 지우지 않는다. 목록에 없는 id는 레벨 0 |
| `meta.unlockedMaxTier` | int | 해금 최고 티어 |
| `meta.runCount` | int | 시작한 런 수 |
| `meta.lastRunIncome`, `meta.bestRunIncome` | double | 직전 런 수입, 최고 런 수입 |
| `meta.totalIncome` | double | 누적 수입 |
| `meta.totalPlayTimeSec` | double | 런 길이 합(상점 시간 제외) |
| `meta.totalPlanets` | int[] | 티어별 누적 생성 수(인덱스 = 티어 − 1) |
| `meta.highestTierCreated` | int | 생성한 최고 티어(0 = 없음) |
| `meta.runHistory` | RunRecord[] | 모든 런. 아래 표 |
| `pending.active` | bool | 진행 중인 런이 있는가 |
| `pending.run`, `elapsed`, `income`, `tierCounts`, `startLevels` | | 진행 중인 런의 번호, 경과 초, 수입, 티어별 개수, 시작 레벨 |

**RunRecord** (`runHistory`의 항목)

| 필드 | 내용 |
|---|---|
| `run`, `durationSec`, `income` | 런 번호, 길이(초), 수입 |
| `tierCounts` | 티어별 생성 수 |
| `ratioVsLast` | 수입 / 직전 런 수입. 첫 런이나 직전 수입 0이면 -1 |
| `startLevels` | 시작 시 id별 레벨 |
| `unlockedMaxTier` | 런 종료 시 해금 최고 티어 |
| `endReason` | `stamina`, `quit`, `crash` |

**settings.json** (사람이 읽는 JSON): `version`, `notation`(0 문자, 1 과학), `pauseOnFocusLoss`. 세이브를 지워도 남는다.

**저장 시점**

| 시점 | pending |
|---|---|
| 런 시작 | 활성 (시작 5초 안에 강제 종료돼도 기록이 남게 하려고 추가) |
| 런 중 5초마다 | 활성 |
| 런 종료(스태미나) | 비활성 |
| 구매 1회, 해금 1회(F6 포함) | 비활성 |
| 앱 종료: 런 중이면 quit 처리 후, 상점이면 그대로 | 비활성 |
| F5 | 상태대로 |
| 다음 실행에서 pending을 crash로 처리한 직후, bak에서 복구한 직후 | 비활성 |

**쓰기와 읽기**
- 쓰기: `save.tmp`에 쓴다 → 기존 `save.json`을 `save.bak`으로 옮긴다 → `save.tmp`를 `save.json`으로 옮긴다. 중간에 꺼지면 `save.bak`이 남는다.
- 읽기: `save.json` → 실패하면 `save.bak` → 둘 다 실패하면 새 게임. 읽지 못한 파일은 `save.corrupt_<시각>.json`으로 옮기고 경고를 남긴다. `"meta"`나 `"version"` 키가 없는 JSON(`{}` 등)도 깨진 것으로 본다.

## 5. 알려진 문제

- **런 중 저장이 메인 스레드에서 파일을 쓴다.** 70런 기록 기준 1회 4.7ms(35KB, 대부분 파일 교체 시간). 5초마다 한 프레임이 늦을 수 있다. 문제가 되면 쓰기를 백그라운드로 옮긴다.
- **에디터의 포커스는 Game view 기준이다.** 런 중 Inspector 같은 다른 패널을 눌러도 일시정지될 수 있다. 빌드에서는 창 포커스 기준이다. 에디터 밖 창 클릭은 개발자가 직접 한 번 확인해 주면 좋다(구현 세션은 외부에서 Unity 창을 활성화하는 방식으로 이벤트를 확인했다).
- **상점은 11행(업그레이드 10 + 해금 1)까지 들어간다.** 업그레이드가 늘면 스크롤이 필요하다.
- **티어 8(짙은 적갈)은 배경과 대비가 낮다.** 비주얼은 3주차.
- **PlayMode 자동 테스트가 없다.** 시작 화면 분기, quit 처리, 포커스 일시정지는 에디터 플레이로 확인했고 테스트는 순수 함수(`Session`, `SaveStore`)까지다.
- **봇은 런 사이에 구매할 때마다 저장한다.** 치트로 재화가 많으면 한 번에 최대 100회 저장한다(1회 약 3ms). 측정용이라 두었다.
- **비용 올림 수정.** `200 × 1.6^2`이 이진 오차로 512.00000000000011이 되어 비용이 513으로 올라가던 것을, 정수에 아주 가까우면(오차 ≤ min(값×1e-12, 1e-6)) 그 정수로 맞추도록 고쳤다. 현재 에셋에서 바뀌는 비용은 먼지 질량 Lv2(513 → 512) 하나다. 1주차 5개 업그레이드의 비용은 바뀌지 않았다.
- **테스트 흔적 정리.** 체크포인트 B·C 검증에 쓴 세이브와 로그는 persistentDataPath의 `week2_tests\`로 옮겼다(save.json, save.bak, save.corrupt_*.json, run_log.csv). 다음 실행은 새 게임으로 시작한다. 1주차 로그는 `run_log_20260918_172341.csv`(헤더 변경으로 자동 이동)와 `run_log_before_C.csv`에 있다.
