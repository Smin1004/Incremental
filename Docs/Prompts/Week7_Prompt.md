# 7주차 작업 프롬프트 (구현 세션용)

아래 블록을 구현 세션에 그대로 붙여 넣는다.

```text
7주차 작업: 궤적, 화면 확장, 성능, 밸런스.

스펙은 Docs/22_Week7_Spec.md 하나다. 먼저 끝까지 읽어라.
배경이 필요하면 Docs/21_Week6_Review.md(6주차 검토와 재조정 목표)와 네가 쓴 Docs/Reports/Week6.md를 본다. 게임 규칙은 Docs/10_Core_Loop.md, 트리 구조와 밸런스 절차는 Docs/12_SkillTree_Spec.md다.

[시작 전에]
1. week6을 main에 병합해라. 6주차 결과는 개발자가 확인했다.
2. persistentDataPath에 개발자가 플레이한 run_log.csv나 save.json이 있으면 지우지 말고 human_playtest_<시각>\ 폴더로 옮겨 보존해라.
3. 커밋되지 않은 Docs/ 기획 문서를 내용은 건드리지 말고 "기획 문서 갱신"으로 커밋해라.
4. main에서 브랜치 scale을 만들어 작업해라.

[작업 순서와 체크포인트]
22 §2 순서대로 한다. 체크포인트마다 EditMode 테스트와 Validate Data를 통과시킨 뒤 커밋한다.
A. 중력원 추종 속도 기본 220과 트리 노드 5개 (22 §3)
B. 빌드 성능 기준선 측정. 고치지 말고 재기만 해라 (22 §4)
C. 소용돌이 성분과 큰 먼지 궤적 리본 (22 §5)
D. 화면 확장: 관문마다 월드 1.06배, 카메라 줌아웃, 먼지 상한 면적 비례 (22 §6)
E. 성능 작업과 상한 정책 (22 §7)
F. 밸런스 재조정 (22 §8)

C와 D가 끝나면 개발자 점검이 한 번 들어간다. 회신을 기다리는 동안 E를 진행해라.

[지킬 것]
- F는 반드시 마지막이다. A~E가 전부 처리량에 영향을 준다.
- F에서 성장축 비율(스태미나, 반경, 먼지 종류)은 첫 완주 전에 한 번 정하고, 그 뒤에는 ringCostMult만 건드려라. 둘을 같이 흔들면 원인을 알 수 없다.
- 먼지 상한은 밸런스 수단이 아니다. §6과 §7이 정한 값을 따른다.
- 성능 목표를 못 채우면 상한을 낮추고 확장 배율을 줄여라. 화면이 비는 것보다 낫다. 낮춘 값과 근거를 보고서에 적어라.
- 새 수치는 전부 데이터 에셋에 둔다. 코드 상수 금지. 시드 코드와 Validate Data도 함께 맞춘다.
- 22 §10(만들지 않을 것)을 지킨다. 특히 특수 능력과 출시 기능은 이번 작업이 아니다.
- 먼지 표류 패턴은 보류다 (22 §11). 소용돌이만 넣고 표류는 건드리지 마라.
- 스펙이 모호하거나 더 나은 방법이 보이면 네 판단으로 진행하고, 보고서의 "스펙과 다르게 했거나 정한 것"에 적는다.
- 기획 결정이 필요한 것을 만나도 멈추지 마라. 합리적인 기본값으로 진행하고 보고서의 "기획이 볼 것"에 적는다.
- 분량이 넘치면 F의 완주 런 횟수부터 줄이고, 줄인 것을 보고서에 적는다.
- 커밋 메시지는 한국어로 쓴다 (CLAUDE.md).

[완료 조건]
22 §9 합격 기준. 사람 눈이 필요한 항목은 스크린샷을 찍어 경로와 함께 "사람 확인 필요"로 넘긴다.

[끝나면]
Docs/Reports/Week7.md를 22 §12 형식으로 쓴다. main 병합은 하지 말고 브랜치 상태로 보고해라.
```

## 이 프롬프트의 판단

- 성능 측정(B)을 앞에 두고 최적화(E)를 뒤에 뒀다. 기준선이 없으면 무엇이 느려졌는지 알 수 없고, 최적화는 궤적과 확장이 올라간 상태에서 해야 의미가 있다.
- 화면 확장이 먼지 수를 2.5배로 늘리므로 성능 목표를 8,000개로 잡았다. 못 채우면 확장 배율을 줄이라고 명시했다. 성능이 규칙보다 우선이다.
- 표류 패턴은 명시적으로 막았다. 소용돌이가 들어가면 체감이 달라지므로 그 뒤에 다시 본다.
