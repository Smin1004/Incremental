# 특수 능력 1차 프로토타입 작업 프롬프트 (구현 세션용)

아래 블록을 구현 세션에 그대로 붙여 넣는다.

```text
특수 능력 1차 프로토타입: 수축, 위성, 유성.

스펙은 Docs/24_Ability_Spec.md 하나다. 먼저 끝까지 읽어라.
배경이 필요하면 Docs/23_Week7_Review.md(7주차 검토)와 Docs/12_SkillTree_Spec.md §5(트리 배치)를 본다.

[이번 작업의 성격]
완성품이 아니라 개발자가 눈으로 확인할 프로토타입이다. 간단하게, 빨리 만든다.
다음은 하지 않는다: 봇 완주 런, 밸런스 조정, 빌드 성능 측정, 새 EditMode 테스트.
기존 EditMode 테스트는 체크포인트마다 돌리지 말고 마지막에 한 번만 돌려라. 시간이 오래 걸린다.
Validate Data는 빠르니 체크포인트마다 돌려도 된다.

[시작 전에]
1. scale을 main에 병합해라. 7주차 결과는 개발자가 확인했다.
2. persistentDataPath에 개발자가 플레이한 run_log.csv나 save.json이 있으면 지우지 말고 human_playtest_<시각>\ 폴더로 옮겨 보존해라.
3. 커밋되지 않은 기획 문서(Docs/, CLAUDE.md)를 내용은 건드리지 말고 "기획 문서 갱신"으로 커밋해라.
4. main에서 브랜치 abilities를 만들어 작업해라.

[작업 순서]
A. AbilityTable, 스탯, NodeKind.AbilityUnlock, 트리 노드 6개 (24 §6, §8)
B. 디버그 키 PageUp / PageDown (24 §7). 이걸 먼저 만들어 두면 C~E를 바로 눈으로 볼 수 있다
C. 수축 (24 §3)
D. 위성 (24 §4). 인력권 밖 먼지 컬링은 반드시 넣는다
E. 유성 (24 §5)
F. 캡처 3장, 기존 테스트 한 번, 보고서
체크포인트마다 Validate Data를 통과시키고 커밋한다.

[지킬 것]
- 능력 하나를 추가하는 일이 "AbilityTable 한 행 + 트리 노드 두 개"로 끝나는 구조로 만든다. 능력은 더 늘어날 수 있다.
- 새 수치는 전부 AbilityTable에 둔다. 코드 상수 금지. 개발자가 인스펙터에서 직접 만져 볼 값이다.
- 능력이 먼지 상한을 넘기게 하지 않는다.
- 24 §10(만들지 않을 것)을 지킨다. 특히 점화 충격파와 23 §6의 작은 것 5건은 이번 작업이 아니다.
- 스펙이 모호하면 간단한 쪽으로 정하고 보고서에 적는다. 멈추지 마라.
- 커밋 메시지는 한국어로 쓴다 (CLAUDE.md).

[끝나면]
Docs/Reports/Abilities_Proto.md를 24 §11 형식으로 짧게 쓴다. 특히 "바로 바꿀 수 있는 값 표"를 빠뜨리지 마라. main 병합은 하지 말고 브랜치 상태로 보고해라.
```

## 이 프롬프트의 판단

- **테스트와 측정을 뺐다.** 개발자가 "간단하게 구현하고 직접 확인", "테스트 돌릴 때 시간이 너무 걸림"이라고 했다. 7주차는 완주 런 10회와 성능 측정으로 시간이 길어졌다. 이번엔 확인이 목적이라 그것들이 필요 없다. 밸런스와 성능은 능력이 확정된 뒤 마지막 밸런스 패스에서 한 번에 한다.
- **디버그 키를 두 번째 순서로 당겼다.** 링 8까지 플레이하지 않고 능력을 볼 수 있어야 확인이 빠르다. 구현 세션 자신도 이 키로 C~E를 확인한다.
- **"바로 바꿀 수 있는 값 표"를 요구했다.** 수축의 힘과 쿨다운처럼 개발자가 만져 보고 정할 값이 많다. 인스펙터에서 바로 바꿀 수 있으면 다음 회신이 빨라진다.
