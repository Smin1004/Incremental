# 빌드 확인 1차 작업 프롬프트 (구현 세션용)

> **따로 보내지 않는다.** 위성 견인과 합쳐 [Satellite_Build.md](Satellite_Build.md)로 보낸다.

2026-10-07. 7주차 이후 빌드를 한 번도 만들지 않았다. 그 사이 빌드에서만 깨질 수 있는 변경이 셋 쌓였다. 개발자 확인이 필요 없는 워커 단독 작업이다.

```text
빌드 확인 1차: 윈도우 빌드, 화면 확인, 성능 재측정. abilities 브랜치에서 이어서 한다.

[왜]
7주차 이후 빌드를 만든 적이 없다. 그 사이 빌드에서만 깨질 수 있는 변경이 셋 쌓였다.
1. 패키지 5개 제거 (능력 3차 C)
2. TextMeshPro 전환과 실행 중 Pretendard 동적 SDF 폰트 생성 (UI 시안 A)
3. 능력, 화면 밖 먼지, 과노출 억제로 먼지 틱과 렌더 비용이 바뀜

[할 것]
A. 윈도우 빌드를 만든다. 7주차의 -perfbench 하네스가 들어가는 같은 구성으로.
B. 빌드를 실행해 확인한다. 한글이 Pretendard로 나오는지, HUD·결과·트리 화면이 에디터와 같게 나오는지, 화면 전환과 능력이 동작하는지. 화면마다 캡처 1장.
C. -perfbench를 돌린다. 7주차 perf_final과 같은 장면에 더해 "런, 먼지 8,000 + 궤적 300 + 능력 전부(최대 레벨) + 화면 밖 먼지" 장면을 하나 추가한다. 7주차 값과 나란히 표로 비교한다.
D. 리눅스 빌드 지원 모듈이 설치돼 있으면 리눅스 빌드도 만들어 실행 파일이 생기는지만 확인한다. 없으면 없다고 적는다.

[지킬 것]
- 고치는 작업이 아니다. 빌드가 깨지거나 화면이 다르게 나오면 최소한으로 고쳐 빌드가 되게만 하고, 무엇을 왜 고쳤는지 적는다.
- 성능이 7주차 목표(먼지 8,000 + 궤적 300에서 평균 60 / 99퍼센타일 50) 아래로 떨어지면 최적화하지 말고 어느 비용이 늘었는지만 적는다.
- CLAUDE.md의 빌드와 성능 규칙을 따른다. com.unity.ai.assistant는 없어야 한다.
- 개발자 세이브는 작업 전에 복사해 두고 끝나면 제자리에 되돌린다. 빌드 실행도 같은 세이브 경로를 쓴다.
- 커밋 메시지는 한국어로 쓴다.

[끝나면]
Docs/Reports/Build_Check1.md에 짧게: 빌드 결과(윈도우, 리눅스), 화면 확인 캡처, 성능 비교 표, 고친 것, 알려진 문제. main 병합은 하지 않는다.
```

## 판단

- **지금 하는 이유:** 능력과 UI가 둘 다 개발자 확인을 기다린다. 워커가 놀고 있고, 이 작업은 개발자가 볼 것이 없다.
- **빌드에서만 깨질 수 있는 것이 셋이다.** 폰트를 실행 중에 만드는 방식은 에디터에서는 되고 빌드에서 안 되는 경우가 흔하다. 패키지 제거도 빌드는 안 해 봤다. 쌓일수록 원인 찾기가 어려워진다.
- **성능 표를 새로 받는다.** 7주차 값은 능력, 화면 밖 먼지, 과노출 억제가 들어가기 전이다. 마지막 밸런스 패스와 출시 판단 때 쓸 기준선이 필요하다.
