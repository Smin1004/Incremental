# 6주차 작업 프롬프트 (구현 세션용)

아래 블록을 구현 세션에 그대로 붙여 넣는다. 즉시 수정(`quickfix1`)이 끝난 뒤에 준다.

```text
6주차 작업: 손맛, 다양성, 밸런스.

스펙은 Docs/20_Week6_Spec.md 하나다. 먼저 끝까지 읽어라.
결정의 배경이 필요하면 Docs/18_Feedback_Round1.md(1차 점검 피드백)와 Docs/19_LowTier_Options.md(하위 티어 대책)를 본다. 게임 규칙은 Docs/10_Core_Loop.md, 트리 구조와 밸런스 절차는 Docs/12_SkillTree_Spec.md다.

[시작 전에]
1. quickfix1을 main에 병합해라. 즉시 수정 결과는 개발자가 확인했다.
2. persistentDataPath에 개발자가 플레이한 run_log.csv나 save.json이 있으면 지우지 말고 human_playtest_<시각>\ 폴더로 옮겨 보존해라.
3. 커밋되지 않은 Docs/ 기획 문서를 내용은 건드리지 말고 "기획 문서 갱신"으로 커밋해라.
4. main에서 브랜치 week6을 만들어 작업해라.

[작업 순서와 체크포인트]
20 §2 순서대로 한다. 체크포인트마다 EditMode 테스트와 Validate Data를 통과시킨 뒤 커밋한다.
A. 먼지 흡인 보정 (20 §3)
B. 먼지 종류: 트리 해금과 확률 노드, 먼지 질량 복리 노드 제거, 세이브 버전 (20 §4)
C. 파편: 트리 노드 6개, 파편과 직접 생성을 따로 세기 (20 §5)
D. 5주차 답 3건과 중력원 추종 속도 실험 토글 (20 §6, §7)
E. 가격 곡선 완화, 비용 재생성, 링별 밸런스 (20 §8)

B가 끝나면 개발자 점검이 한 번, D가 끝나면 한 번 더 들어간다. 점검 회신을 기다리는 동안 다음 순서를 진행해라.

[지킬 것]
- E는 반드시 마지막이다. A~D가 전부 경제에 영향을 준다.
- B에서 노드 id가 바뀌므로 5주차 스냅샷은 무효다. 새 스냅샷은 E의 절차에서 만든다.
- E는 개별 노드 비용을 손으로 만지지 않는다. 20 §8.2 공식으로 재생성하고, 조정은 ringCostMult만 쓴다.
- 새 수치는 전부 데이터 에셋에 둔다. 코드 상수 금지. 시드 코드와 Validate Data도 함께 맞춘다.
- 20 §10(만들지 않을 것)을 지킨다. 특히 특수 능력은 이번 작업이 아니다.
- 스펙이 모호하거나 더 나은 방법이 보이면 네 판단으로 진행하고, 보고서의 "스펙과 다르게 했거나 정한 것"에 적는다.
- 기획 결정이 필요한 것을 만나도 멈추지 마라. 합리적인 기본값으로 진행하고 보고서의 "기획이 볼 것"에 적는다.
- 분량이 넘치면 E의 링 조정 반복 횟수부터 줄이고, 줄인 것을 보고서에 적는다.
- 커밋 메시지는 한국어로 쓴다 (CLAUDE.md).

[완료 조건]
20 §9 합격 기준. 사람 눈이 필요한 항목은 스크린샷을 찍어 경로와 함께 "사람 확인 필요"로 넘긴다.

[끝나면]
Docs/Reports/Week6.md를 20 §11 형식으로 쓴다. main 병합은 하지 말고 브랜치 상태로 보고해라.
```

## 이 프롬프트의 판단

- 5.5일짜리라 지금까지 중 가장 크다. 순서를 어기면 밸런스를 두 번 하게 되므로 "E는 마지막"을 두 번 적었다.
- 점검을 두 번 끼워 넣었다. 먼지 종류와 파편은 눈으로 봐야 판단할 수 있고, 개발자가 불편한 상태로 오래 기다리지 않게 하려는 것이다.
- 스냅샷이 무효가 되는 것을 미리 적었다. 모르고 옛 스냅샷으로 측정하면 측정값이 전부 틀린다.
- 특수 능력은 명시적으로 제외했다. 개발자가 착수 직전에 다시 논의하기로 했다.
