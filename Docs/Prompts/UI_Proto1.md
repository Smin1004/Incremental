# UI·연출 시안 작업 프롬프트 (구현 세션용)

2026-10-01. 26 §6의 1단계(시안)다. 능력 확인은 개발자가 미뤄 두었으므로 그동안 진행한다.

```text
UI·연출 시안: 폰트와 UI 기반, 결과 화면, 스태미나 두 안. abilities 브랜치에서 이어서 한다.

스펙은 Docs/26_UI_Pass_Spec.md다. 먼저 끝까지 읽어라. 이번 작업은 §6의 1단계(시안)만이다.

[이번 작업의 성격]
프로토타입이다. 개발자가 보고 시각 방향을 고르게 하는 것이 목적이다.
봇 완주 런, 밸런스 조정, 빌드 성능 측정, 새 EditMode 테스트는 하지 않는다.
기존 EditMode 테스트는 마지막에 한 번만 돌린다. Validate Data는 체크포인트마다 돌린다.

[작업 순서]
A. 기반 (26 §4)
   - Pretendard(OFL)를 프로젝트에 넣고 라이선스 파일도 같이 둔다.
   - UIBuilder.CreateText를 TextMeshPro로 바꾼다. Pretendard 동적 SDF 폰트 에셋으로 한글이 나와야 한다. 숫자는 고정폭으로 보이게.
   - UITheme ScriptableObject를 만들고, 결과 화면과 HUD의 색 상수를 옮긴다(트리는 다음 단계).
   - UI 셰이더 하나로 패널과 버튼을 그린다. 매개변수로 방향 A(관측 기기: 얇은 선, 모서리 브래킷, 눈금), B(유리: 반투명, 둥근 모서리, 가장자리 빛), C(패널 없음, 글자와 그림자만)를 표현한다.
B. 결과 화면 (26 §5.2): 새 패널과 버튼, 수입 굴러 올라감, 배율 색, 최고 기록 배지, 행성 미니 아이콘(PlanetVisual 재사용), 행 순차 등장.
C. 런 HUD 스태미나 (26 §5.1): (a) 새 스타일 막대, (b) 중력 고리를 스태미나 게이지로. 둘을 전환할 수 있게.
D. 디버그 키: UI 방향 A/B/C 전환, 스태미나 (a)/(b) 전환. 비어 있는 키를 골라 쓰고 보고서와 F1 오버레이에 적는다. 지금 쓰이는 키는 F1~F12, Insert, Home, End, Space, PageUp/PageDown, 숫자 0~4, -, =다.
E. 캡처: 결과 화면 A/B/C 3장, 같은 런의 HUD 스태미나 (a)/(b) 2장(잔량 70%와 15%면 4장). 기존 테스트 한 번, 보고서.
체크포인트마다 커밋한다.

[지킬 것]
- 트리 화면, 화면 전환, 월드 연출(과노출 등)은 이번 작업이 아니다. 방향이 정해진 뒤에 한다.
- 텍스처와 아이콘 그림을 쓰지 않는다. 셰이더와 글자로만.
- UI의 빛과 움직임도 연출 강도(F11)를 따른다.
- Space 두 번이면 3초 안에 다음 런(R7)이 깨지지 않게 한다. 결과 화면 등장 연출은 Space로 즉시 넘어간다.
- 새 수치와 색은 전부 UITheme이나 기존 데이터 에셋에. 코드 상수 금지.
- 능력과 위성은 건드리지 마라. 개발자 확인 전이다.
- 스펙이 모호하면 간단한 쪽으로 정하고 보고서에 적는다. 멈추지 마라.
- 커밋 메시지는 한국어로 쓴다 (CLAUDE.md).

[끝나면]
Docs/Reports/UI_Proto.md에 짧게 쓴다: 만든 것, 확인 방법(키), UITheme에서 바로 바꿀 수 있는 값 표, 캡처 목록, 스펙과 다르게 한 것, 알려진 문제. main 병합은 하지 않는다.
```

## 판단

- **방향을 말로 고르지 않고 시안에서 고르게 했다.** 개발자는 "보고 판단"하는 쪽이다. 셰이더 매개변수만 바꾸면 되므로 세 안을 같이 만드는 비용이 작다.
- **결과 화면 하나에만 먼저 입혔다.** 패널, 버튼, 숫자, 목록이 다 있어서 스타일을 판단하기에 가장 정보가 많은 화면이다.
- **스태미나 (b)를 넣었다.** 홀드 비율 0.92라 플레이어 눈은 거의 항상 중력원에 있다. 위쪽 막대는 거의 보지 않는다. 다만 체감은 직접 봐야 알 수 있어 토글로 비교한다.
- **능력 확인과 겹치지 않게 했다.** 개발자가 능력 확인을 미뤘으므로 워커가 쉬는 동안 시안을 만든다. 능력 코드는 건드리지 않는다.
