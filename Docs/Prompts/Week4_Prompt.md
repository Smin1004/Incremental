# 4주차 작업 프롬프트 (구현 세션용)

아래 블록을 구현 세션에 그대로 붙여 넣는다. 같은 세션에 이어서 줘도 되고 새 세션에 줘도 된다.

```text
4주차 작업: 행성 비주얼.

스펙은 Docs/14_Planet_Visual_Spec.md 하나다. 먼저 끝까지 읽어라.
배경이 필요하면 Docs/README.md(문서 색인), Docs/10_Core_Loop.md(게임 규칙), Docs/13_Result_SolarSystem_Spec.md(결과 화면), 그리고 네가 쓴 Docs/Reports/SkillTree_Step1.md와 Week3_Tree_SolarSystem.md를 본다. 그 두 보고서에서 기획에 물은 것의 답은 14 §8에 있다.

[시작 전에]
1. 커밋되지 않은 Docs/ 기획 문서가 있다(12, 13, 14, Prompts 등). 내용은 건드리지 말고 "기획 문서 갱신"으로 한 번 커밋해라.
2. main에서 브랜치 planet-visuals를 만들어 작업해라.

[작업 순서와 체크포인트]
14 §2 순서대로 한다. 체크포인트마다 EditMode 테스트와 Validate Data를 통과시킨 뒤 커밋한다.
A. 행성 셰이더, 티어별 외형 데이터, 갤러리 디버그 키 (14 §3)
B. 형성 중인 천체 (14 §4)와 먼지 외형 (14 §5)
C. 항성 점화, 배경 팔레트, 연출 강도 디버그 키 (14 §6)
D. 결과 화면 연결과 성장 강조 (14 §7)
E. 규칙 변경 2건과 링 1~3 재측정 (14 §8). 0.5일을 넘기지 마라.

[지킬 것]
- 텍스처 파일을 만들거나 가져오지 않는다. 전부 셰이더와 수식이다.
- 새 수치는 전부 데이터 에셋에 둔다. 코드 상수 금지. 시드 코드와 Validate Data도 함께 맞춘다.
- 섬광과 빛 번짐은 전부 effectIntensity를 곱한다.
- 게임 규칙은 14 §8의 2건 외에는 바꾸지 않는다. 14 §10(만들지 않을 것)을 지킨다.
- 스펙이 모호하거나 더 나은 방법이 보이면 네 판단으로 진행하고, 보고서의 "스펙과 다르게 했거나 정한 것"에 적는다.
- 기획 결정이 필요한 것을 만나도 멈추지 마라. 합리적인 기본값으로 진행하고 보고서의 "기획이 볼 것"에 적는다.
- 분량이 넘치면 14 §2 순서의 뒤에서부터 자르고, 자른 것을 보고서에 적는다.
- 커밋 메시지는 한국어로 쓴다 (CLAUDE.md).

[완료 조건]
14 §9 합격 기준. 사람 눈이 필요한 항목(구분되는가, 읽히는가)은 스크린샷을 찍어 경로와 함께 "사람 확인 필요"로 넘긴다.

[끝나면]
Docs/Reports/Week4_Visuals.md를 14 §11 형식으로 쓴다. main 병합은 하지 말고 브랜치 상태로 보고해라. 병합은 내가 확인한 뒤에 한다.
```

## 이 프롬프트에 담은 판단

- 스펙 문서 하나만 읽으면 되게 했다. 프롬프트 본문에는 규칙과 순서만 둔다.
- 체크포인트를 5개로 나눈 것은 1~3주차 보고서의 체크포인트 A, B, C 방식이 잘 작동했기 때문이다.
- "멈추지 말고 기본값으로 진행 후 보고"는 지금까지의 작업 방식 그대로다.
- 병합을 보류시킨 이유: 이번 주차는 눈으로 봐야 하는 결과물이라 개발자가 갤러리와 런 화면을 직접 본 뒤 병합하는 편이 안전하다.
